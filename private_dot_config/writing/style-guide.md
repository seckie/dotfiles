# 文体ガイド

状態: 初稿案（4文書での観察に基づく。本人の恒常的な好みとしては未確認）
更新日: 2026-11-10

## 適用範囲

ユーザー名義の日本語の文書の作成・推敲に用いる。分析対象は、技術的な利用手順の README（資料A）、社内向けガイドライン（資料B）、公開ブログの体験・レビュー記事（資料C）、イベント参加レポート（資料D）。英語本文、コードそのもの、第三者の引用文、サイトのナビゲーションなど本文以外の表示は文体の根拠から除いた。D の発表メモは整理の構造を分析し、登壇者由来の主張や語彙を本人の好みとして扱わない。

通常の会話には、明示的に依頼された場合に適用する。今回指定された読者・目的・文体を優先する。公開記事は体験・レビューとイベントレポート各1本を分析しており、メール、提案書、その他のジャンルへの適用は未検証。

## このガイドの使い方

- 用途に近い[本人の文例](examples.md)と[添削記録](revisions.md)を参照する。
- 以下の「観察できた特徴」は対象文書内の事実であり、本人が承認済みの文体ルールという意味ではない。執筆時の暫定的な指針として用いる。
- 仮説は確定した好みとして扱わない。
- AI の草稿が修正されなかったことだけを根拠に、本人の好みと判断しない。
- 今回だけの修正と、今後も適用する好みを区別する。
- 資料A・Bは社外秘のため、本ガイド・文例・添削記録にはその原文、社内固有名、内部 URL を保存しない。根拠は抽象化した観察と資料内の位置で記録する。公開資料C・Dは、本人の許可に基づき出典と原文の短い抜粋を文例に保存する。
- 技術文書の語調を個人記事へ一律に適用しない。以下の根拠と用途別の指針を確認して使い分ける。

## 観察できた特徴と執筆時の指針案

以下は対象の4文書で確認できた特徴。指針案はその特徴を再現するための提案。根拠の対応は[分析記録と公開文例](examples.md)を参照する。

### 構成・説明の順序

- 技術文書では、冒頭で対象と目的・機能を示し、その後に利用や判断に必要な情報を置く。
  - 根拠: A は短い機能紹介の後に利用事例、準備、設定、動作、開発の情報を並べる。B は目的と背景を説明した後に禁止・遵守・推奨を分ける。
- 章全体の順序は文書の用途に合わせる。
  - 指針案: 利用手順では導入から実行へ、規範文書では目的から行動規範へ進める。体験記事では背景と動機から判断・体験・評価へ進める。
- 原則や操作だけでなく、理由、条件、具体例を近くに添える。
  - 根拠: A の準備手順・設定の説明、B の各規範の補足。理由が先に置かれる例もあり、常に結論先行とは限らない。
- 個人の体験・レビュー記事では、生活上の背景と選択の理由を語ってから、体験を観点別に掘り下げる。
  - 根拠: C は前年の生活の振り返り、購入動機、比較検討と接客の体験から、機能別のレビューへ進み、最後に生活の変化と今後の展望へ戻る。
  - 指針案: 冒頭から評価を要約する型に固定せず、その体験に至る事情も本文として扱う。
- イベントレポートでは、参加した日時・催し・記録の位置付けを簡潔に説明し、セッション別のメモ、筆者の所感へ進める。
  - 根拠: D は参加報告とメモの共有を宣言し、セッションと論点ごとに記録した後、明示的な区切りを置いて感想と自分の意欲を述べる。
  - 指針案: 記録部分と自分の解釈・感想を分ける。全体を均一な解説記事へ書き直すことを前提にしない。

### 語彙・表記

- 技術用語や製品名、設定名は原語を保ち、日本語で役割や操作を説明する。
  - 根拠: A の設定表・操作説明、B の用語の定義・具体策。
- 略称は初出付近で定義し、補足や例を括弧に入れる。
  - 根拠: B の冒頭と遵守事項、A の設定・実行例の導入。
- 手順や規範では、動詞で具体的な行為を示す。
  - 指針案: 読者が何を設定し、確認し、実行するかを明記する。抽象的な説明だけで終わらせない。
- 設定名・コマンド・パスはインラインコード、実行例はコードブロックで区別する。
  - 根拠: A の設定・実行説明、B の操作例。表記の細かな揺れや誤記は文体の好みとして再現しない。
- 個人記事では一人称や日常語を交え、専門用語を自分の体験や感覚と結び付けて説明する。
  - 根拠: C の一人称は「僕」。技術的な機能の列挙に、操作の楽さ、怖さ、振動などの体感や、過去の自分との比較を添える。
  - 指針案: 体験を表す具体的な言葉を使う。C で用いられた比喩や言い回し自体を定型句にはしない。
- 個人記事の話題の接続には、日常的な接続表現を使う。
  - 根拠: C は因果、余談、追加、留保を会話的につなぎ、括弧内で補足や自問を挟む。
  - 指針案: 段落のつながりに応じて用い、各段落へ機械的に挿入しない。
- 発表メモでは、話題や問いを短く置き、その下に要点・補足・具体例をまとめる。
  - 根拠: D は論点や質問を起点に入れ子の箇条書きを使い、一部では組織名や登壇者名を括弧で添える。
  - 指針案: 固有名は発言の帰属を示す用途で使う。登壇者の比喩・口語・価値判断を、筆者の定型表現として採用しない。プログラム由来と思われる見出しも本人の語彙の証拠にはしない。

### 語尾・断定の強さ

- 技術文書A・Bは常体が中心。説明の言い切り、動詞の終止形、体言止めを併用する。
  - 根拠: A の機能紹介・操作手順・設定表、B の目的・行動規範。
- 手順・規範の指示や禁止は、読者が取るべき行動を直接示す。
  - 指針案: 必要な場面で行為の禁止、義務、指示を明記し、不要に婉曲化しない。
- 必須・推奨・目安・通常時を区別し、強さを使い分ける。
  - 根拠: B の要求レベルと推奨事項、A の設定説明にある条件・通常時の説明。
- 手順・規範では推奨を義務へ、想定を保証へ書き換えない。要件としての強い断定は必要な箇所に限定する。
- 個人記事Cは敬体を基調に、感想や強調で常体・体言止めを交える。
  - 根拠: C の導入や体験説明は敬体。感嘆、短い感想、連続する観測値などには別の語尾も使われる。
  - 指針案: 全文を事務的な常体や、均一な敬体に揃えず、意味とリズムに合わせる。
- イベントレポートDでは、導入と所感は敬体、発表メモは常体・体言止め・疑問形などの短い記述が中心。最後の自分の決意にはくだけた常体を使う。
  - 指針案: 筆者が語る部分と情報を記録する部分で語調を使い分ける。発表メモ内の断定・命令を、筆者自身が読者へ求める行動に変えない。
- 個人の体感、原因についての推測、伝聞を語尾で書き分ける。
  - 根拠: C の走行性能の評価では体感と推測を分け、機構の説明には伝聞の語尾も使う。一方で、本人の驚きや好みは率直に言い切る箇所がある。
  - 指針案: 体験を一般的な性能保証に広げない。原因が未確認なら推測として示し、直接の感想まで一律に弱めない。

### 文の長さ・段落・箇条書き

- 独立した説明は短い段落に分ける一方、複数の条件・理由がある項目は複数文で説明する。
  - 根拠: A の設定表には長い説明もある。B は短い原則に補足の箇条書きを続ける。
- 順序や分岐がある操作・処理には番号付きリストを使う。
  - 根拠: A の準備手順と処理の説明。
- 並列する規則、選択肢、補足には箇条書きを使う。対象ごとの具体策は必要に応じて入れ子にする。
  - 根拠: B の禁止事項と推奨する具体策、A の利用事例。
- 同じ属性で比較する設定項目は表にし、説明・既定値・必須性を揃える。
  - 根拠: A の設定表・入力項目表。
- 一律の文字数制限や、入れ子の全面禁止は設けない。条件と結果の関係を追えることを優先する。
- 個人記事Cは見出しと散文の段落が中心で、本文に箇条書きや表を使っていない。複数の出来事・条件を一段落で追う長い説明もある。
  - 指針案: 話題や評価の観点で段落を分ける。体験の流れや語りの間を、すべて短文や箇条書きに置き換えない。
- イベントレポートDは見出しと入れ子の箇条書きを中心にし、導入と所感を散文にする。メモでは主語や述語、句点を省いた短い項目も使う。
  - 指針案: セッション・論点・要点・補足の関係を階層で示す。読み手が追える範囲でメモの簡潔さを保ち、すべてを完全文に揃えない。表や番号付き手順を必須にはしない。
- 長い説明の途中や末尾に、短い感想や余韻のある一文を挟む。
  - 根拠: C の接客の体験、運転支援の留保、燃費の説明では、具体的な説明に短い反応や軽いユーモアを添える。
  - 指針案: 内容に合う場面でのみ用い、感嘆や三点リーダーを必須の装飾にしない。

### 好む表現・避けたい表現

本人が明示的に好む・避けたいと指定した表現は、現時点では未登録。対象文書に出現する表現をそのまま必須語彙にしたり、出現しない表現を禁止したりしない。

### 強調・参照の使い方

- 注意すべき規範や操作対象を強調し、補足の参照先を該当箇所の近くに置く。
  - 根拠: A の画面操作と運用文書への参照、B の要求レベルと参考情報。
- 指針案: 引用した仕様と、その仕様から読者に求める行動を分けて書く。引用元の文章を本人の文体として模倣しない。
- 太字、色、下線、記号などの具体的な装飾は、媒体や文書の用途に合わせる。すべての文書への一律適用はしない。
- イベントの概要や案内への参照を導入に置き、記録の出所と筆者の所感を区別する。
  - 根拠: D の導入にはイベントへのリンクがあり、メモの一部には発言元の注記がある。最後に記録の終了を明示してから所感へ移る。
  - 指針案: メモを逐語録とはみなさず、話者が明記されていない要点の発言者を推測で補わない。

## 用途別の違い

| 用途 | 対象文書での特徴 | 執筆時の指針案 |
| --- | --- | --- |
| 利用・設定を説明する README | 機能を短く紹介し、利用事例、準備、設定例、動作、開発情報へ進む。番号付き手順、設定表、コード例が中心。 | 読者が実行できるだけの具体性を持たせる。条件、既定値、制約を操作の近くに記載する。詳細な運用は別文書への参照で補う。 |
| 社内向けガイドライン | 目的と背景から入り、禁止・遵守・推奨を分ける。短い原則に理由と具体策を添える。 | 期待する行動と要求の強さを明示する。理由や例を添え、読者が判断・実行できるようにする。 |
| 個人の体験・レビュー記事 | 背景・動機・比較検討から体験の評価へ進む。敬体を基調に一人称、会話的な接続、感想を交える。見出しと散文が中心。 | なぜ選んだか、何を経験し、どう感じたかを具体的に語る。長所と限界、体感と推測を分け、利用条件や数値を評価に添える。最後は生活や考え方の変化へ戻る構成も選べる。 |
| イベント参加レポート | 日時・催し・記事の位置付けを示し、セッションと論点ごとのメモを掲載した後、筆者の所感へ移る。敬体の語りと短い発表メモを使い分ける。 | 入れ子の箇条書きで情報を整理し、発言元が分かる箇所は示す。記録と自分の受け止めを区別し、最後に印象や今後の意欲を短く添える。 |

技術資料の体裁には英語の見出しや併記もあるが、日本語部分だけを分析した。英日併記を本人の普遍的な好みとは判断しない。C の観測値や機能の記述、D の当時の発表内容は歴史的な記録として扱い、現在の仕様・性能・業界動向の根拠には用いない。

## 仮説・未確認の特徴

- 読者が行動・判断できることを、文章の装飾や語り口より重視している可能性がある。
  - 根拠: A・Bで操作・規範・具体策が多い。ただし技術文書に限った仮説であり、語り口や余談を含むCには一律に適用しない。
- 前提を共有する技術者を想定し、一般的な技術用語の解説を省く傾向がある可能性がある。
  - 適用は読者次第。初学者向けの説明にも同じ省略を持ち込まない。
- 簡潔さは重視していても、必要な条件・理由・例を削るほどの短さは求めていない可能性がある。
  - 根拠: A・Bでは短い原則と長い設定説明が共存し、Cでも動機・具体例・留保を段落で詳しく語る。
- 用途をまたいで、判断や評価に理由・条件・具体的な経験を添える傾向がある可能性がある。
  - 根拠: A・Bの条件や理由の説明に加え、Cでも選択の理由や使用条件ごとの評価を語る。ただし、本人の恒常的な好みとしての確認はまだない。
- 公開記事では、体験の紹介・記録の後に、自分の受け止めや今後への気持ちを添える傾向がある可能性がある。
  - 根拠: C は生活の変化と翌年への展望、D は登壇内容を聞いた感想と自分の意欲で締める。C・Dとも筆者が語る部分は敬体を基調に一人称を交えるが、本文の形式は散文と発表メモで異なる。
- 絵文字、色分け、英語の見出しなどを恒常的に好むかは未確認。文書のテンプレートや組織内の慣例の影響を切り分けられない。
- 公開記事は2020年と2022年の各1本のみ。現在も同じ語調を好むか、別の題材でも同じ構成を取るかは未確認。メール、提案書、その他のジャンルは追加の文例が必要。

## 更新・共有の手順

1. 原文を保存してよい資料は文例に、添削前後と理由は添削記録に残す。社外秘の資料は原文を転載せず、抽象化した分析記録にする。
2. 一般化できる好みと適用範囲を整理し、確認済みか仮説かを区別して本ガイドを更新する。
3. この一式は chezmoi の `private_dot_config/writing/` を正本として編集し、差分を確認して配置先の `~/.config/writing/` に反映する。配置先を直接編集した場合は、その変更を正本に取り込む。
4. ChatGPT にアップロードして利用する場合は、3ファイルをまとめた配布版 `writing-guide.md` を作成し、更新日を添えてプロジェクトのファイルを差し替える。配布版への修正も正本に戻す。
